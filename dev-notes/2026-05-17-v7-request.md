## Fix 1 — `set_model` wire field

`PiRpcClient.set_model(provider, model)` currently sends:

```json
{"type": "set_model", "provider": "...", "model": "..."}
```

Pi's RPC schema actually wants the field to be named `modelId`, not `model`. See `packages/coding-agent/src/modes/rpc/rpc-types.ts:31` in the pi source. With the current shape pi silently does nothing — no error, no model change — so this can drift without anyone noticing.

Please:

- Change the wire frame to `{"type":"set_model","provider":"...","modelId":"..."}`.
- Rename the Python parameter to `model_id` for clarity, or keep `model` but transform on the way out — your call.
- Add a regression test that pins the exact wire shape (e.g., fake-pi captures the JSON and asserts `modelId` is present and `model` is not).

## Fix 2 — manifest `protocolVersion` handshake

The bridge has no version handshake right now. If the Python side and the TS shim drift, we get confusing runtime errors deep inside `execute`. Please add a tiny handshake at the front:

- Define a constant `MANIFEST_PROTOCOL_VERSION = 1` in `tools.py` (or wherever the manifest is built).

- Include it in the `manifest` response payload:

  ```json
  {
    "id": "m1",
    "type": "response",
    "success": true,
    "data": {
      "protocolVersion": 1,
      "tools": [...]
    }
  }
  ```

- In the TS shim, hardcode `SUPPORTED_PROTOCOL_VERSION = 1` and immediately after the manifest call, assert `manifest.protocolVersion === SUPPORTED_PROTOCOL_VERSION`. On mismatch, throw a clear error during extension load. Mention in a comment that the convention is to bump this constant on any backwards-incompatible change to the manifest / `execute` / `update` / `response` frame shapes.

- A test that the shim assertion fires on mismatch is welcome but not required.

## New piece — an `Agent` class with `on_*` hooks

The substantive addition. I want a Template-Method-style class that subclassers extend to react to pi events (`tool_call`, `tool_result`, `agent_start`, `agent_end`, `message_*`, etc.). Hooks should default sync — most casual users will write `def on_tool_call(self, event): log.info(...)` and shouldn't have to know about asyncio. But an async escape hatch should exist for users who legitimately need to do async work in a hook (e.g. issuing another bridge call, awaiting a downstream service).

Here's the shape I want.

### Two parallel hook names per event, both declared on the base class

For every event we expose, declare **both** `async_on_{event}` and `on_{event}` as class attributes on `Agent`, defaulted to `None`:

```python
class Agent:
    _EVENT_NAMES: ClassVar[tuple[str, ...]] = (
        "tool_call",
        "tool_result",
        "agent_start",
        "agent_end",
        # ... etc — see "open question 1" below
    )

    # Default surface — every name declared, both colors, all None.
    async_on_tool_call: AsyncHookProtocol | None = None
    on_tool_call: SyncHookProtocol | None = None
    async_on_tool_result: AsyncHookProtocol | None = None
    on_tool_result: SyncHookProtocol | None = None
    # ... etc.
```

Spell every declaration out literally — no metaclass codegen, no `__init_subclass__` magic for populating the defaults. Even if the event list is 10+ entries, the explicit form is what I want for this pass. We can revisit metaprogramming later if the verbosity bites.

### Subclass overrides exactly one per event

Common case:

```python
class MyAgent(Agent):
    def on_tool_call(self, event):
        log.info("tool: %s", event["name"])

    async def async_on_agent_end(self, event):
        await self.export_session_html("/tmp/last.html")
```

Defining both `async_on_X` and `on_X` for the same event should be an error at class construction time. Use `__init_subclass__` to check; raise `TypeError` with a clear message naming the conflicting event.

A subclass that inherits an async handler from its parent and wants to switch to a sync one in a deeper subclass does:

```python
class B(A):
    async_on_tool_call = None  # explicitly clear the inherited handler
    def on_tool_call(self, event):
        ...
```

The `__init_subclass__` check sees only `on_tool_call` is non-`None` and accepts it.

### `__init_subclass__` should also catch typo'd hook names

If a subclass defines an attribute named `async_on_*` or `on_*` whose suffix is not in `_EVENT_NAMES`, raise. This catches `def on_tool_cal(self, event)` (typo) which would otherwise silently never be called. Useful enough to justify the validation cost.

### Dispatcher: async wins; sync goes through the executor

Internal dispatch lives on the runtime loop thread. The async wrapper looks up the bound handlers via direct attribute access (no `getattr` with a default — the names always exist because we declared them):

```python
async def _async_on_event(self, event):
    name = event.type  # whatever pi calls it — string identifier
    async_handler = getattr(self, f"async_on_{name}", None)
    if async_handler is not None:
        await async_handler(event)
        return
    sync_handler = getattr(self, f"on_{name}", None)
    if sync_handler is not None:
        await self._loop.run_in_executor(self._hook_executor, sync_handler, event)
        return
    if self._raise_on_unhandled_event:
        raise UnhandledEventError(f"no handler defined for event of type {name!r}")
    # otherwise: silent no-op
```

(`getattr` with a `None` default is fine; the point is the name always exists so we don't need to *guard* for absence — `None` is the sentinel.)

### Sync hooks go to a dedicated executor

Don't reuse the tool `ThreadPoolExecutor`. A dedicated `_hook_executor` per `HarnessRuntime`, `max_workers=1`. Two reasons:

- Tool pool contention would let a slow tool starve event delivery.
- `max_workers=1` plus the dispatcher's `await` per event preserves strict per-agent event ordering with no extra machinery.

The sync hook's return value is discarded. Document this in the docstring.

### Strict mode opt-in

A class attribute `_raise_on_unhandled_event: bool = False`. Default off. Pi may emit event types we haven't taught `Agent` about; strict-by-default would break forward-compatibility on pi upgrades. Users who want the safety net set it to `True` on their subclass.

### Lower-level events still reachable

Whatever the new `Agent` class does, please keep `PiRpcClient.on_event(handler)` and `next_event()` working. Users who don't want the subclass-with-hooks pattern should still be able to subscribe at the lower level. The new `Agent`'s dispatcher is a *new* subscriber on top, not a replacement.

### Tests

At least these:

- `__init_subclass__` raises when a subclass defines both `async_on_X` and `on_X` for the same event.
- `__init_subclass__` raises when a subclass defines an `async_on_*` or `on_*` attribute whose suffix isn't in `_EVENT_NAMES`.
- An async hook fires on the loop thread (assert via `threading.current_thread() is the loop thread`).
- A sync hook fires on the hook executor thread (assert via thread name or `not the loop thread`).
- "Switch-color" subclass: `B(A)` clears the inherited async, defines sync; the sync runs on a fake event.
- Strict mode set to `True` on a subclass; a fake event with no handler raises `UnhandledEventError`.

## What I want you to figure out (open questions)

Make a call and explain in the design doc. I'm fine being surprised; just be explicit.

1. **The event set.** Which pi event types should `Agent` expose as named hooks? Use the pi source as the canonical reference — the events emitted by the agent loop. Include a short table in the design doc with each event name and one line on when it fires. Events you receive but don't expose as named hooks should still be reachable via the lower-level `client.on_event(handler)` plumbing. Better to start with a focused set than to expose everything pi can possibly emit.

1. **`Agent` vs `PiAgentHarness` relationship.** Two viable shapes — pick one:

   - *Inheritance*: `class Agent(PiAgentHarness)`. One object; user subclasses, defines hooks, calls `agent.start()` / `agent.prompt(...)`.
   - *Composition*: `class Agent` holds a `PiAgentHarness` instance. Two objects to wire together.

   Inheritance is simpler for the user; composition is more flexible (one agent could in principle drive multiple harnesses). I lean inheritance for v1 unless you see a reason composition matters more.

1. **Event payload shape.** Right now `_dispatch_event` passes through raw `dict[str, Any]` from pi. For the hook API, do you expose `event: dict[str, Any]` or define a typed `@dataclass` per event type? Typed is friendlier but doubles the surface. Recommend; default to raw dict if the taxonomy is fluid.

1. **Lifecycle wiring.** When does the dispatcher subscribe to the client? Probably during `Agent.start()` after the client exists. Spell out the sequence in the design doc.
