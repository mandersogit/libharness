# Design: Python-first Pi harness using RPC and a generated TypeScript bridge

## Goals

- Author tools in Python.
- Author environment customization and workflow policy in Python where possible.
- Keep any TypeScript to a small, generated adapter.
- Use Pi's real agent harness rather than reimplementing an agent loop.
- Support deterministic integration tests without requiring an external LLM.

## Non-goals for the initial implementation

- Replacing Pi's TypeScript extension system.
- Implementing all of Pi's TUI customization in Python.
- Providing a complete MCP server/client.
- Shipping a production sandbox for untrusted tools.

## Architecture

```text
+-------------------------+       JSONL stdin/stdout       +---------------------------+
| Python application      |  --------------------------->   | Pi CLI --mode rpc         |
|                         |                                 |                           |
| - PiRpcClient           |  <---------------------------   | - AgentSession            |
| - workflow policy       |       responses + events        | - provider/model runtime  |
| - state integration     |                                 | - tool registry/loop      |
+-------------------------+                                 +-------------+-------------+
                                                                      |
                                                                      | ExtensionAPI.registerTool()
                                                                      |
                                                        +-------------v-------------+
                                                        | Generated TS extension    |
                                                        |                           |
                                                        | - starts Python server    |
                                                        | - lists Python tools      |
                                                        | - forwards tool calls     |
                                                        +-------------+-------------+
                                                                      |
                                                                      | JSONL stdin/stdout
                                                                      |
                                                        +-------------v-------------+
                                                        | Python tool server        |
                                                        |                           |
                                                        | - ToolRegistry            |
                                                        | - decorated Python tools  |
                                                        | - normalized ToolResult   |
                                                        +---------------------------+
```

There are two separate protocols:

1. **Pi RPC protocol** between the Python host and Pi.
2. **Python tool protocol** between the generated TS shim and the Python tool server.

Keeping them separate avoids overloading Pi's RPC protocol and keeps the bridge easy to test.

## Component responsibilities

### `PiRpcClient`

File: `pi_python_harness/rpc.py`

Responsibilities:

- Launch Pi as a subprocess with `--mode rpc`.
- Write LF-delimited JSON objects to stdin.
- Parse LF-delimited JSON objects from stdout.
- Correlate `type: "response"` messages by `id`.
- Dispatch asynchronous Pi events to handlers and an event queue.
- Handle extension UI requests by either delegating to a Python callback or returning cancellation for dialog-like requests.

Current methods include:

- `start()` / `stop()`
- `send(command)`
- `prompt(message)`
- `prompt_and_wait(message)`
- `get_state()`
- `get_messages()`
- `get_commands()`
- `bash(command)`
- `export_html(output_path)`
- `next_event()`

### `ToolRegistry`

File: `pi_python_harness/tools.py`

Responsibilities:

- Register Python functions as Pi-compatible tools.
- Infer simple JSON Schema parameter definitions from Python type hints.
- Accept explicit schemas for complex tools.
- Normalize return values to Pi-compatible tool results.
- Serve tools over the bridge JSONL protocol.

Example:

```python
from pi_python_harness import ToolResult, tool

@tool(prompt_snippet="Echo text from Python")
def py_echo(message: str) -> ToolResult:
    return ToolResult.text(f"python echo: {message}")
```

### Generated TypeScript shim

File generated by `write_python_tool_shim()`.

Responsibilities:

- Start a persistent Python subprocess.
- Request the Python tool manifest by sending `{"method":"list_tools"}`.
- Register each manifest entry with `pi.registerTool()`.
- On tool execution, send `{"method":"call_tool", ...}` to Python.
- Return the Python result to Pi's agent loop.
- Register a small diagnostic slash command.
- Stop the Python server during session shutdown.

The shim should remain generic. It should not contain project-specific tool logic.

### Python tool server protocol

Requests are LF-delimited JSON objects.

List tools:

```json
{"id":"ts_1","method":"list_tools"}
```

Response:

```json
{
  "id": "ts_1",
  "ok": true,
  "tools": [
    {
      "name": "py_echo",
      "label": "Py Echo",
      "description": "Echo a message through Python.",
      "parameters": {
        "type": "object",
        "properties": {"message": {"type": "string"}},
        "required": ["message"],
        "additionalProperties": false
      },
      "promptSnippet": "Echo text from Python"
    }
  ]
}
```

Call tool:

```json
{
  "id": "ts_2",
  "method": "call_tool",
  "name": "py_echo",
  "toolCallId": "toolu_123",
  "cwd": "/work/project",
  "params": {"message": "hello"}
}
```

Response:

```json
{
  "id": "ts_2",
  "ok": true,
  "result": {
    "content": [{"type": "text", "text": "python echo: hello"}],
    "details": {"message_length": 5}
  }
}
```

Error response:

```json
{
  "id": "ts_2",
  "ok": false,
  "error": "ValueError: ...",
  "traceback": "..."
}
```

## Tool result contract

Python tools may return:

- `ToolResult`
- a mapping with a `content` field
- any other mapping, which is serialized as text JSON
- any scalar, which is stringified into a text result
- `None`, which becomes an empty text result

A Pi-compatible result is:

```python
{
    "content": [{"type": "text", "text": "..."}],
    "details": {},
    "terminate": False,  # optional
}
```

## Schema strategy

The bridge emits JSON Schema, not TypeBox objects. This works because Pi's validation code can handle plain JSON Schema-like objects. The initial inference supports common hints:

- `str` -> `{"type":"string"}`
- `int` -> `{"type":"integer"}`
- `float` -> `{"type":"number"}`
- `bool` -> `{"type":"boolean"}`
- `list[T]` -> array schema
- `dict[...]` -> object schema
- `Optional[T]` / `T | None` -> nullable schema
- broader unions -> `anyOf`

Complex or constrained schemas should be passed explicitly to `@tool(parameters=...)`.

## Launch flow

1. Python app creates a temporary or cached TS shim file.
2. Python app launches Pi with:

```text
pi --mode rpc --extension /path/to/generated/python-tools.ts ...
```

3. Pi loads the extension through its extension loader.
4. The shim spawns the Python tool server.
5. The shim asks Python for the tool list and calls `pi.registerTool()` for each one.
6. The Python app sends prompts and control commands over Pi RPC.
7. If the model emits a tool call, Pi invokes the shim's `execute()` function.
8. The shim forwards the call to Python and returns the normalized result to Pi.
9. Pi emits normal tool execution events over RPC.

## Concurrency and cancellation

The initial shim supports multiple pending bridge requests and correlates them by id. It does not yet propagate cancellation to Python. A production version should add:

- `cancel_tool` messages from TS to Python when Pi's `AbortSignal` fires.
- A `ToolContext.cancelled` or `asyncio.Event` exposed to Python tool functions.
- Configurable max concurrent Python tool calls.
- Timeouts per tool and per manifest request.

## Security model

Pi extensions and Python tools run with process-level authority. Treat both as trusted code. Recommended controls:

- Run from a controlled working directory.
- Restrict active tools with Pi's `--tools` option or equivalent configuration.
- Keep tool subprocess environment minimal.
- Avoid loading arbitrary Python modules from writable locations.
- Log tool names, arguments, duration, and result sizes.
- Add policy gates in Python before calling Pi `prompt()` or before registering high-risk tools.

## Production hardening backlog

1. Cancellation propagation.
2. Structured logging and trace ids across Pi RPC and tool bridge RPC.
3. Tool server restart and health-check policy.
4. Schema conformance tests against Pi validation for every registered Python tool.
5. Optional UNIX-domain socket transport for long-running high-volume tool servers.
6. Explicit resource limits for tool execution.
7. Per-tool security policy and active-tool allowlist.
8. Better UI handler support for extension select/input/editor requests.
9. Wheel packaging with a helper command that generates the shim into a cache directory.
10. Version compatibility tests for supported Pi releases.
