# v8 → `libharness.pi` port plan

Executable implementation plan for adopting v8 (decision hooks + opt-in participation, with the `AgentHookSurface` mixin refinement) as the new base of `src/libharness/pi/`. Sister doc: `dev-notes/2026-05-17-v8-analysis.md`, which sets the design and the author resolutions. This doc translates that into file-level work, commit boundaries, and validation checkpoints.

This branch (`asyncio-in-thread` on the spark machine) is the implementation surface. The matching design exploration sits on the original `asyncio-in-thread` branch on the desktop checkout. The port currently lands here because spark has the codex-cli adversarial review skill that fits the implementation pass.

## TL;DR

Vendor v8 source into `src/libharness/pi/`, rename the namespace, apply the `AgentHookSurface` mixin refinement from `agent_class_mca.py`, close the 38-declaration gap, split the agent class into three files, add a consistency-check helper, **cherry-pick three pre-identified v8 bugs with regression tests, run a 3-reviewer adversarial review on the source-side work**, port the v8 tests, address items C and E from the analysis, then update the docs that describe the now-superseded direction. Ten-to-twelve commits, ~1500 LOC net, four validation checkpoints (three build/test runs across two venvs + one adversarial-review gate).

## Preconditions before starting

Verify each in order. None should fail; if one does, stop and investigate before continuing.

- Branch is `asyncio-in-thread` (or whatever spark labels the implementation branch). Confirm via `git branch --show-current`.
- Working tree clean. Confirm via `git status`.
- `make all` green on baseline (3.11). Confirm via `make all`.
- `make test-live` green on baseline. Optional but recommended — pins the v5 baseline as the "before" state so any regression during the port is unambiguously port-introduced.
- `dev-notes/predecessors/v8-decision-hooks/` is present and intact. Confirm via `ls dev-notes/predecessors/v8-decision-hooks/src/pi_python_harness/`.
- The author-refactored mixin variant exists at `dev-notes/predecessors/v8-decision-hooks/src/pi_python_harness/agent_class_mca.py`. This is the layout-of-record for the port; do **not** start from `agent_class.py`.

## File-level inventory

What changes, what's new, what stays.

### Files added (new in `src/libharness/pi/`)

| File              | Source                                        | LOC  |
| ----------------- | --------------------------------------------- | ---- |
| `runtime.py`      | v8 verbatim                                   | ~220 |
| `agent.py`        | v8 verbatim                                   | ~495 |
| `events.py`       | extract from `agent_class_mca.py`             | ~80  |

| `agent_class.py`  | residual from `agent_class_mca.py`            | ~150 |

**Detail:**

- *`runtime.py`:* the dedicated asyncio loop thread + shared tool executor + per-harness owner thread machinery. v6/v7/v8 all share this layout; v8's copy is the most recent and is what we're vendoring.
- *`agent.py`:* the thread-owned proxy. Holds `bridge_event_handler`, `initial_open_gates`, `decision_timeouts_ms` constructor params and threads them into `PythonToolServer`. `HarnessSnapshot` is the public fact-bag for introspecting threading state in tests.
- *`events.py`:* the public data types hook authors interact with. Frozen dataclasses, no upward imports. Smallest of the three new files.
- *`hook_surface.py`:* the `AgentHookSurface` mixin. Hosts the four frozensets, config attrs, the four hook type aliases, **all 112 hook ClassVars** (76 from v8's mixin variant + 36 new for the decision-event observation slots — see § Gap closure), and the four `_validate_*` classmethods. Imports `AgentEvent` and `HookContext` from `events.py`.
- *`agent_class.py`:* the `Agent` class. Reads as `class Agent(AgentHookSurface, PiAgentHarness)`. Holds `__init_subclass__`, `__init__`, `start`, `close`, the dispatchers (`_async_on_event`, `_async_on_bridge_event`, `_dispatch_notification_hook`, `_dispatch_decision_hook`), the install/uninstall helpers, manifest wiring (`_initial_open_gates_for_class`, `_decision_timeouts_for_manifest`), and the module helpers `_call_decision_handler` + `_handler_wants_context`. Imports `AgentHookSurface` from `hook_surface.py`.

## Phased sequencing — nine commits

Each phase is a single commit through the **commit-plans** skill. The phases are ordered so that each commit leaves the tree in a buildable, `make all`-green state. Validation gates are inserted at three points; if a gate fails, the failure isolates to ≤3 commits.

### Phase 1 — Vendor + rename

**Commit:** `feat(pi): vendor v8 source as libharness.pi (decision hooks + opt-in participation)`

Action:

- Copy `dev-notes/predecessors/v8-decision-hooks/src/pi_python_harness/*.py` into `src/libharness/pi/`.
- Use `agent_class.py` (the original v8 file, not the mixin variant) so Phase 1 = "v8 verbatim, renamed". Mixin refinement is its own phase.
- Replace `pi_python_harness` → `libharness.pi` in every `from` / `import` and in any string references.
- Update `src/libharness/pi/__init__.py` to re-export the v8 public surface (see § File-level inventory).
- Do **not** touch tests yet — Phase 1 ships source only. `make all` will fail on test discovery until Phase 6; that's expected and the reason Phase 1+2+3+4+5 sit behind the first validation gate, not a per-commit gate.

Why this order: a clean "v8 as-is" commit at the start gives a stable rebase target if any later phase needs to be redone. It also makes the diff for later phases small and readable.

**Files added:** `runtime.py`, `agent.py`, `agent_class.py`. **Files updated:** `__init__.py`, `server.py`, `shim.py`, `tools.py`. **Files possibly updated:** `rpc.py`, `harness.py`, `jsonl.py` (only if v8 has real diffs vs current; confirm and include if so).

### Phase 3 — Close the 38-declaration gap

**Commit:** `feat(pi): declare observation hooks for decision events`

Action:

- In `agent_class.py` (still single file), add 38 ClassVar declarations to the `AgentHookSurface` body: for each of the 19 `_DECISION_EVENT_NAMES`, add both `on_<event>: ClassVar[SyncAgentHook | None] = None` and `async_on_<event>: ClassVar[AsyncAgentHook | None] = None`.
- Place them inside the existing four quadrants — sync `on_<decision_event>` go into the sync-notification block, async ones into the async-notification block. Maintain alphabetical order within each block or follow the existing event ordering from `_EVENT_NAMES` / `_DECISION_EVENT_NAMES`; pick one rule and apply it consistently.
- Total ClassVars after this phase: 112 (was 74 in v8; was 76 in `agent_class_mca.py` — same as 74, the mixin variant didn't add the gap-closers).

Why this order: this is the only phase that adds new declarative surface; isolating it makes the diff easy to audit and means if the validation-classmethod logic ever needs to know "is this a notification-only event or a notification-on-decision event", the answer comes from the frozensets, not from inspecting ClassVar presence.

**Acceptance:** import-time validation still passes on a vanilla `Agent` subclass; the count `sum(1 for n in dir(AgentHookSurface) if n.startswith(('on_', 'async_on_', 'decide_', 'async_decide_'))) == 112`.

### Phase 5 — Consistency-check helper

**Commit:** `feat(pi): assert hook-surface declarations match event sets at import time`

Action:

- In `hook_surface.py`, add a module-level helper `_assert_declarations_match_event_sets(cls: type[AgentHookSurface]) -> None` that runs on `AgentHookSurface` itself at import time (after the class body) and asserts:
  - Every name in `_EVENT_NAMES` has `on_<name>` and `async_on_<name>` ClassVars declared on `AgentHookSurface` (not inherited).
  - Every name in `_DECISION_EVENT_NAMES` has all four: `on_<name>`, `async_on_<name>`, `decide_<name>`, `async_decide_<name>`.
  - No ClassVar starting with `on_` / `async_on_` / `decide_` / `async_decide_` exists for a name **not** in the appropriate frozenset.
- Raise `AssertionError` with the missing/extra names if any mismatch is found. The helper is ~15-25 lines.

Why this order: with the gap closed (Phase 3) and the surface in its final shape (Phase 4), this is the first phase where the consistency invariant is true and worth pinning. Running it at import time means future drift (adding an event to `_EVENT_NAMES` without adding the declarations) is a load-time failure, not a runtime mystery.

**Acceptance:** importing `libharness.pi` succeeds; intentionally adding a fake event name to a frozenset in a scratch branch produces an `AssertionError` naming the missing declarations.

### Phase 5.5 — Cherry-pick known v8 bugs

**Commit:** `fix(pi): cherry-pick three v8 bugs surfaced in threads-rewrite review`

Three bugs the `threads-rewrite` Claude caught during its phase 2-3 adversarial reviews on the parallel branch (origin/threads-rewrite). Verified against v8 source at file:line. Each ships with its regression test in the same commit. Source: `dev-notes/2026-05-17-claude-recommendations-for-v8-port.md`.

| Bug                                          | Location         | Severity |
| -------------------------------------------- | ---------------- | -------- |
| dict-merge order in UI response frame        | `rpc.py:411`     | CRITICAL |
| `params or {}` falsy coercion                | `server.py:235`  | HIGH     |
| orphaned reader tasks on startup-probe abort | `rpc.py:178-183` | MODERATE |

**Detail:**

- *dict-merge order (Check 1):* v8 builds the response as `{"type": "extension_ui_response", "id": request_id, **response}`. Later keys override earlier ones in `**` unpacking — a UI handler returning `{"id": "EVIL", "type": "evil-type", ...}` silently overrides the framework's correlation id and type. Pi receives a response addressed to the wrong request. **Fix:** swap to `{**response, "type": "extension_ui_response", "id": request_id}` so the framework keys win. **Regression test:** UI handler returns `{"id": "EVIL", "type": "evil-type", "confirmed": True}`; the written wire frame must have `id == "real-1"` and `type == "extension_ui_response"`.
- *`params or {}` falsy coercion (Check 4):* v8 reads `params = request.get("params") or {}` at `server.py:235`, then asserts `isinstance(params, dict)` on the next line — but the `or {}` already coerced `[]`, `0`, `""`, `False` to `{}` before the type check. Malformed clients pass silently. **Fix:** `params = request.get("params", {})`, then `if params is None: params = {}`, then the existing `isinstance` check raises. **Regression test:** four parametrized cases sending `params=[]`, `params=0`, `params=""`, `params=False`; each must surface as a wire-level error response, not a silent dispatch with empty params.
- *orphaned reader tasks (Check 7):* v8's startup probe at `rpc.py:178-183` checks `process.returncode is not None` and raises `PiRpcProcessError`, but the two reader tasks (`_reader_task`, `_stderr_task` created at lines 176-177) are not cancelled and the process handle isn't reaped. Task leak; subsequent tests inherit dangling tasks. **Fix:** wrap the probe in try/except that closes `process.stdin`, cancels both reader tasks, awaits `asyncio.gather(*reader_tasks, return_exceptions=True)`, calls `await process.wait()` with a small timeout, then re-raises the original `PiRpcProcessError`. **Regression test:** mock a pi binary that exits immediately with code 1; assert `PiRpcProcessError` is raised AND `_reader_task.done()` AND `_stderr_task.done()` AND `process.returncode is not None`.

Why this phase: these three bugs are pre-identified, low-risk to fix, and the regression tests pin the behavior so the subsequent reviewer pass (Gate A.5) doesn't re-flag them. Bundling all three in one commit keeps the cherry-pick boundary clean — the commit message can cite the recommendations doc and the threads-rewrite synthesis docs by file:line.

**Acceptance:** the three new regression tests pass; `make all` still green on both venvs.

### --- Validation gate A.5 — 3-reviewer adversarial review ---

The plan's other gates verify "did the code build and run." This gate verifies "did reviewers find bugs that tests don't catch." v8 hasn't been through one; the threads-rewrite Claude's review loop caught ~20 must-fix bugs per phase on the parallel branch. The bug classes (silent wire-shape corruption, subtle ordering races, MRO mistakes, lock-order hazards) are not what `make all` finds.

Process (~half-day total):

1. **Write a 500-800 word implementation summary** to `/tmp/v8-port-implementation-summary.md`. Cover: what changed from v5 baseline, what changed from v8 verbatim (the Phase 5.5 fixes specifically), the design decisions (3-file split, 112 ClassVars, gate model, mixin extraction). The summary primes reviewers without making them re-derive context.
1. **Spawn 3 reviewers in parallel:** 2× codex gpt-5.5 xhigh + 1× Opus subagent. Use the prompt template from `dev-notes/2026-05-17-claude-recommendations-for-v8-port.md` § Phase-level review-gate recommendation. Each reviewer reads in order: this port plan, the v8 analysis, the implementation summary, the diff vs `main`, the current source under `src/libharness/pi/`. Each writes findings to `/tmp/v8-port-review-<reviewer-id>.md` scored CRITICAL / HIGH / MODERATE / MINOR with file:line citations.
1. **Synthesize findings** into `dev-notes/2026-05-17-v8-port-review-synthesis.md`. Group by tier; flag multi-reviewer agreement explicitly (a finding that all three reviewers raise has different signal than one reviewer's hunch). Use `../libharness/dev-notes/2026-05-16-threads-rewrite-plan-phase{2,3}-review-synthesis.md` as the format template — both are accessible from this checkout now that the threads-rewrite branch has been fetched.
1. **Apply Tier-1 fixes** (CRITICAL + multi-reviewer HIGH) in a follow-up commit `fix(pi): apply v8-port adversarial review Tier-1 findings`. If reviewers find no Tier-1 issues beyond what Phase 5.5 already fixed, this commit is the synthesis doc alone (`docs: v8-port adversarial review synthesis`).
1. **Re-run flake check** on both venvs (3 consecutive runs each = 6 runs total) to verify no regressions from any Tier-1 fixes.

**Acceptance:** synthesis doc committed; any Tier-1 findings have either been fixed (with regression tests) or deferred with explicit reasoning in the synthesis doc; full test suite green across all 6 flake runs.

If this gate fails: a CRITICAL or multi-reviewer HIGH was found and the fix attempt surfaced a regression. Either revert the fix and push deeper into the root cause, or escalate the finding back to the reviewers with the partial-fix diff for a second pass. Don't proceed to Phase 6 until the gate passes — the rest of the port shouldn't ride on top of known-bad code.

## Risk register

Concrete things that could go sideways during the port, with mitigations.

| Risk                                                       | L   | S   | Mitigation                  |
| ---------------------------------------------------------- | --- | --- | --------------------------- |
| `rpc.py` has subtle v5→v8 diffs we miss                    | low | med | side-by-side diff in P1     |
| Live test flakiness on 3.14t                               | low | med | bisect by venv              |
| `subscribe_client_events` simplification regresses         | med | low | revert if breaks P6         |
| Wire-frame field names diverged from prompt                | low | low | keep v8 names               |
| `MANIFEST_PROTOCOL_VERSION` rename breaks handshake        | low | low | rerun handshake test        |
| 38 new ClassVars hide a typo in event names                | low | med | P5 consistency check        |
| Mixin MRO surprises (`AgentHookSurface`, `PiAgentHarness`) | low | med | layout already tested in v8 |

**Detail:**

- *`rpc.py` subtle diffs:* run `diff -u src/libharness/pi/rpc.py dev-notes/predecessors/v8-decision-hooks/src/pi_python_harness/rpc.py` in Phase 1; review every changed hunk before deciding to copy or keep. Same drill for `harness.py` and `jsonl.py`.
- *Live test flakiness on 3.14t:* the asyncio core stays single-threaded in v8 (one loop thread), so FT mostly only buys parallelism for the tool executor pool. Most v8 logic runs the same on 3.11 and 3.14t. A failure on one but not the other is signal worth chasing — capture logs, look for race conditions exposed by FT, do **not** paper over with retries.
- *`subscribe_client_events` simplification regresses:* the v7 thread-bounce (analysis § Discussion C, carried forward to v8 § Items E) is the "owner thread → loop thread → list.append" round-trip. The simplification is to do the append on the loop thread directly. If it breaks a test, revert that part and ship Phase 6 without it — item E is "nice to have", not a port blocker.
- *Wire-frame field names diverged:* v8 uses `{"event": "...", "data": {...}}` whereas the analysis prompt sketched `{"event_name": "...", "event_data": {...}}`. Pi never sees these — they're internal Python↔TS bridge frames. Keep v8's choice; no rename needed.
- *`MANIFEST_PROTOCOL_VERSION` rename:* the promotion to a named constant in Phase 1 must not break the existing handshake test (`test_real_pi_integration.py` or wherever `protocolVersion=1` is asserted). Re-run it after Phase 1 if Gate A doesn't catch it.
- *38 new ClassVars hide a typo:* the Phase 5 consistency check catches any typo in the `on_<event>` / `async_on_<event>` declarations at import time. Verify by manually breaking one in a scratch branch — should raise `AssertionError` at import.
- *Mixin MRO surprises:* v8 ships and tests `Agent(AgentHookSurface, PiAgentHarness)`; the mixin variant in `agent_class_mca.py` already works. If `super().__init__` chains break during the port, root-cause via `Agent.__mro__` and the `__init_subclass__` chain.

## Out of scope for this port

Explicitly **not** included. If any of these become urgent, they get their own follow-on plan.

- **Runtime opt-in for decision events** (`agent.enable_decision_for(...)` / `disable_decision_for(...)`). Author-deferred. The gate set is fixed at extension load.
- **Per-event TypedDicts** for decision-hook return shapes. Documentation-only contract for v1.
- **Pi-native session method wrappers** (`fork`, `clone`, `switch_session`, `get_session_stats`, `export_html`, `set_session_name`, `get_fork_messages`). Independent task; queued in SESSION-STATE.md.
- **Command bridge, state bridge, UI bridge.** Future bridges that ride on the same TS-shim plumbing v8 establishes. Roadmap-level.
- **Shim-side `DECISION_EVENTS` array drift detection** (analysis § Items B). The Python-side `test_pi_event_taxonomy.py` already catches Python-side drift; TS-side drift detection is a future hardening pass.
- **Decision hook exception logging dedup** (analysis § Items A). Cosmetic; not a port blocker.
- **`_handler_wants_context` heuristic edge cases** (analysis § Items D). The canonical signatures behave correctly; edge cases get docstring treatment, not code changes.
- **`PiPythonHarness` deprecation.** Stays for v1 of the port per author resolution.
- **Defaulting `_decision_timeout_ms` to a non-`None` value.** The sibling recommendations doc (`2026-05-17-claude-recommendations-for-v8-port.md`) proposes defaulting to `30000` ms so a buggy `decide_X` can't wedge pi indefinitely. Deliberately rejected for v1: human-in-the-loop decision hooks may legitimately need to block for hours or days (the human is away from the computer). Defaulting to 30s would assume human-not-in-the-loop, which we're not willing to bake in. Users who want a bounded timeout opt in by setting `_decision_timeout_ms` or `_decision_timeouts_ms` on their `Agent` subclass — the opt-in mechanism is already in place. Revisit if a real wedge-from-bug incident materializes; the recommendation is sound for the non-HITL case.
