# v8-decision-hooks — analysis

Analysis of the v8 follow-on revision the agent produced in response to `dev-notes/2026-05-17-v8-request.md`. The package is vendored at `dev-notes/predecessors/v8-decision-hooks/`. This doc compares the deliverable to the spec, flags judgment calls and minor concerns, and recommends next steps.

## TL;DR

**v8 cleanly hits the brief.** Every locked decision in the request register honored. Decision hooks for all 19 participation events, both `decide_X` and `async_decide_X` flavors, all symmetric with the existing 18 notification hooks. The subscribe-to-all + always-notify + gated-decide architecture is implemented end-to-end (Python + TS shim + bridge protocol). Method-existence opt-in trigger works. Cancellation via `HookContext` is wired through. Timeout is opt-in via class attributes. Channel separation is preserved and explicitly tested. mypy strict + pyright basic + ruff clean; 36 passed (1 skipped on the real-pi gate), up from v7's 18.

The agent made defensible judgment calls on every open question, including the `_OBSERVABLE_EVENT_NAMES = _EVENT_NAMES | _DECISION_EVENT_NAMES` validation decision that allows users to write `on_tool_call` to observe a decision event without opening the gate.

**Post-review refinements were applied in-tree** (see `agent_class_mca.py` in v8): a mixin class (`AgentHookSurface`) was extracted to separate the declarative hook surface from the Agent class's dispatch logic, and the literal hook declarations were reorganized into four colocated blocks (sync notification → sync decision → async notification → async decision) for better navigability. See § Post-review refinements below.

**One real gap surfaced during review:** v8 declares `on_X` / `async_on_X` only for the 18 RPC notification events, not for the 19 decision events. The validation accepts observation hooks for decision events (the mechanism is wired), but the slots are not declared on the mixin. This means IDE autocomplete won't suggest them and type-checkers won't recognize them as overrides. Closing the gap means adding 38 more ClassVar declarations (112 total instead of 74). See § Gap below.

**Recommendation:** port v8 into `src/libharness/pi/` as the new base, adopting the `AgentHookSurface` mixin layout. Close the gap during port. Consider a 3-file split for the port (`events.py` / `hook_surface.py` / `agent_class.py`). See § Recommendation for the libharness port.

## Architecture: how the gate model materialized

The end-to-end participation flow is clean. For each pi participation event:

1. **Shim subscribes at load.** `shim.py:314-324` registers `pi.on(eventName, handler)` for every event in the `DECISION_EVENTS` array.
1. **Gate check in the shim handler.** `shim.py:264-303` `handleDecisionEvent` reads `openGates` set (populated from manifest's `initialOpenGates`):
   - Gate closed → `bridgeNotify(...)` fire-and-forget; returns `undefined` to pi immediately.
   - Gate open → `bridgeCall(...)` with optional per-event timeout; returns the result to pi.
1. **Fail-open on bridge errors / timeouts.** Wrapped in try/catch; on error or timeout, shim returns `undefined` (treat as no opt-in for this fire). Pi proceeds normally; log captures the failure.
1. **Python-side handling.** `server.py:183-190` dispatches by request type. Both routes flow to `event_handler` (which is `Agent._async_on_bridge_event`).
1. **Agent dispatcher.** `agent_class.py:263-282` `_async_on_bridge_event`:
   - Validates event name against `_DECISION_EVENT_NAMES`.
   - Runs notification hook first (if `on_X` / `async_on_X` defined).
   - If `require_decision=True` (gate-open path), creates `HookContext`, runs decision hook, returns result.
1. **Manifest wiring.** Agent's constructor (`agent_class.py:234-239`) passes `bridge_event_handler`, `initial_open_gates`, and `decision_timeouts_ms` through to `PiAgentHarness`, which threads them into `PythonToolServer`'s manifest output.

The wire frames diverge slightly from my prompt sketch — the agent used field names `event` (name) and `data` (payload) instead of `event_name` / `event_data`. Functionally identical; I didn't lock the exact field names.

## Notable judgment calls the agent made

These are the spots where v8 picked an approach we didn't fully prescribe.

### 1. Cancellation API: optional `ctx: HookContext` second positional

The agent introspects the hook's signature (`_handler_wants_context` at `agent_class.py:468-484`) to detect whether the user wants `ctx` passed. Detection rules:

- Has `*args` → pass ctx.
- Two or more positional/positional-or-keyword params → pass ctx.
- `ctx` or `context` as a keyword-only param → pass ctx.
- Otherwise → don't pass.

```python
# Common case: no ctx
def decide_tool_call(self, event) -> dict: ...

# Cancellation-aware: opt-in
def decide_session_before_switch(self, event, ctx: HookContext) -> dict | None:
    if ctx.cancelled:
        return None
    ...
```

This is a thoughtful resolution. The user pays no cost for ctx unless they want it. Detection by signature inspection is slightly clever but well-documented. The downside: a hook that accidentally uses `*args` for currying or partial application will get ctx whether it wants it or not. Edge case; unlikely to matter.

### 2. Timeout configuration: both global and per-event

`agent_class.py:149-150` declares both `_decision_timeout_ms` (one value for all opted-in events) and `_decision_timeouts_ms: dict[str, int]` (per-event overrides). `_decision_timeouts_for_manifest` (`agent_class.py:374-380`) merges them: global applies to all open gates first, then per-event entries override.

I suggested in the prompt that one or the other was fine; the agent shipped both. Slight redundancy but no downside — users who want simple get the global; users who want per-event get the dict; users who want both get the natural override behavior.

### 3. `_OBSERVABLE_EVENT_NAMES = _EVENT_NAMES | _DECISION_EVENT_NAMES`

`agent_class.py:145`. This means `on_tool_call` (observation hook for a decision event) is a *valid* hook name — separate from the question of whether opening the gate.

Concretely: a user who wants to *observe* `tool_call` events without ever blocking them defines `on_tool_call(self, event)` and does NOT define `decide_tool_call`. The shim still sends `notify_event` (gate closed, fire-and-forget). Notification hook fires. No round-trip, no pi block.

This is a nice bonus. The spec said "user gets full visibility regardless of opt-in" but didn't fully specify the API affordance. The agent picked the cleanest answer: same `on_X` name as for notification events. Mental model: "an `on_X` always observes; a `decide_X` chooses to gate." One pattern across both surfaces.

### 4. Module organization: kept everything in `agent_class.py`

The prompt left this open ("fold into `agent_class.py` or split into `decision.py`"). The agent kept it consolidated. Reasonable — the `Agent` class IS the public surface; splitting would create import gymnastics for one class. The file is ~490 lines; not yet at refactor-pressure.

### 5. Per-event return-shape documentation in `AGENT_HOOKS.md`

`docs/AGENT_HOOKS.md` lines 178-198 has the full per-event return-shape table — every one of the 19 decision events mapped to its expected dict shape with a concrete example. Cites pi-mono `extensions/types.ts:978-1041` for the source. Critical for users; this is the table I asked for and the agent delivered exactly.

## Gap: observation hooks for decision events are not declared on the mixin

The most consequential issue found during review. The spec asked for full symmetry: every observable event should have notification hooks declared as ClassVars defaulted to `None`. v8 declares `on_X` / `async_on_X` for the 18 RPC notification events but **not** for the 19 decision events.

**What v8 actually does:**

- `_EVENT_NAMES` (18 RPC notification events): both `on_X` and `async_on_X` declared on the mixin (36 ClassVars).
- `_DECISION_EVENT_NAMES` (19 decision events): only `decide_X` and `async_decide_X` declared (38 ClassVars).
- Total: 74 ClassVars.

**What was implicitly contracted:**

- 18 RPC notification events: `on_X` + `async_on_X` declared (36 ClassVars).
- 19 decision events: `on_X` + `async_on_X` + `decide_X` + `async_decide_X` declared (76 ClassVars).
- Total: 112 ClassVars.

The 38 missing ClassVars are the observation slots for decision events.

**How the mechanism handles this today:**

`_validate_declared_hook_names` accepts `on_<decision_event>` and `async_on_<decision_event>` as valid names because `_OBSERVABLE_EVENT_NAMES = _EVENT_NAMES | _DECISION_EVENT_NAMES` (`agent_class.py:145`). The dispatcher at `_async_on_bridge_event` calls `_dispatch_notification_hook(wrapped, strict=False)` before the decision-hook step, which finds an `on_X` via `getattr` and fires it. So a user who *knows* to define `on_tool_call` will get observation behavior — both when the gate is closed (notify_event path) and when the gate is open (observe-then-decide order).

The IMPLEMENTATION JOURNAL explicitly acknowledges this asymmetry:

> The implementation keeps `_EVENT_NAMES` as the 18 RPC notification events and `_DECISION_EVENT_NAMES` as the 19 in-process extension events, while validation accepts observation hooks for the union.

ChatGPT made the validation permissive but did not add the declarations. The mechanism works; the declarative surface doesn't reflect it.

**Why this matters:**

- IDE autocomplete (Pyright, Pylance, JetBrains analyzers) reads class bodies. A user typing `on_` in their `MyAgent(Agent)` subclass will see suggestions for `on_agent_start`, `on_agent_end`, etc., but NOT `on_tool_call`, `on_resources_discover`, etc. They have to know to type the full name without help.
- Type-checkers may not recognize `on_tool_call(self, event)` on the subclass as an override of a base-class declaration, possibly missing signature-mismatch errors.
- New users reading the mixin file see the full hook surface for notification events but a half-surface for decision events. The conceptual model "every observable event has all four hook flavors" isn't visible in the source.

**Fix:** add 38 more ClassVar declarations to bring the total to 112. Specifically, for each of the 19 decision events, add:

```python
on_<event>: ClassVar[SyncAgentHook | None] = None
async_on_<event>: ClassVar[AsyncAgentHook | None] = None
```

Mechanical change; doesn't affect any v8 behavior. Just makes the declarative surface match the contracted one.

## Post-review refinements (in-tree, applied to v8 after the initial review)

After the initial review of v8, two organizational changes were applied to the v8 source as `agent_class_mca.py` to clean up the file structure. These are author-applied; not part of ChatGPT's output.

### Refinement 1: extract hook declarations into an `AgentHookSurface` mixin

The 74 hook ClassVar declarations plus the supporting frozensets and config attrs are moved into a separate `AgentHookSurface` class. `Agent` inherits from both: `class Agent(AgentHookSurface, PiAgentHarness)`.

Benefits:

- Separates the **declarative hook surface** (what hooks exist) from the **Agent class's behavior** (dispatch logic, lifecycle, validation). Two different reasons to change, two different classes.
- The `Agent` class body becomes much easier to scan — ~70 lines of static declarations no longer sit between `__init__` and the dispatchers.
- MRO is clean: `AgentHookSurface` is plain (just class attrs and the validation classmethods, no instance state), so `super().__init_subclass__(**kwargs)` threads correctly through both bases. The validation classmethods (which can live on the mixin) reach class attrs via standard MRO lookup.
- The mixin can host the consistency-check helper (see below) without polluting the Agent class.

Naming note: the mixin is `AgentHookSurface` (no leading underscore). Public, on the theory that the hook surface is part of the library's public contract — third parties may inspect or subclass it, and the rest of the public API (`Agent`, `AgentEvent`, `HookContext`, `UnhandledEventError`) doesn't use underscore prefixes. If we want to revisit this and re-introduce the underscore (committing to "implementation detail; don't import directly"), that's still on the table during the port.

### Refinement 2: reorder hook declarations into four quadrants

ChatGPT's original layout interleaved `async_on_X` with `on_X` for each event (and similarly `async_decide_X` with `decide_X`). The reorganization groups by color: all sync notification first, then all sync decision, then all async notification, then all async decision.

Rationale: when a user picks a hook to write, they pick *one* flavor — sync OR async. Under the interleaved layout, every line of the mixin has to be eye-filtered to "is this the variant I want?" Under the quadrant layout, the 99% sync user reads only blocks 1 and 2; the async user reads only blocks 3 and 4. **Each user reads half the file as relevant; the other half is invisible noise to them.**

The "blocks 3-4 are mechanical mirrors of blocks 1-2" framing is the load-bearing argument — once you understand the symmetry rule (every hook has both a sync and an async variant), blocks 3-4 contain no new information. Single-line comment headers (`# Sync notification hooks`, etc.) above each block make the structure obvious to first-time readers.

The mutual-exclusivity rule ("don't define both `on_X` and `async_on_X` for the same event") is enforced at class-construction time with a clear error message naming the conflict. Visual proximity of the two declarations was a decorative cue, not load-bearing.

### Refinement 3 (proposed but not yet applied): close the 38-declaration gap

Add the missing 38 observation ClassVars for decision events. See § Gap above.

## Items worth discussing before porting

None of these are blockers. All are micro-concerns.

### A. Decision-hook exception bubbles up further than expected

Notification hooks: try/except + log + swallow (correct — observation can't change pi behavior, so silent recovery is fine).

Decision hooks: try/except + log + **re-raise** (`agent_class.py:323-324`, `337-339`). The re-raise propagates through `_dispatch_decision_hook` into `_async_on_bridge_event`, out to `server.py`'s `_dispatch_bridge_event`, which catches and returns a failure response. The shim sees the failure response and returns `undefined` to pi (fail-open).

Result: a raising `decide_X` does end up fail-open from pi's perspective, but the exception is logged twice (Python side via `_LOG.exception`, then potentially again via server's bridge response). Mostly cosmetic — both logs are useful for debugging. Worth mentioning in the docstring of `_dispatch_decision_hook` so users grepping logs aren't surprised by duplicate entries.

### B. Shim-side `DECISION_EVENTS` array isn't validated against pi source

`shim.py` hardcodes the 19 decision event names in a TS array (`shim.py:79-99`). If pi adds a new participation event in a future release, the Python `_DECISION_EVENT_NAMES` set is checked by `test_pi_event_taxonomy.py`, but the TS array is not. Drift between the two could mean: pi has a new event, Python knows about it via taxonomy regen, but the shim doesn't subscribe to it.

Mitigation idea (future, not v8): generate the `DECISION_EVENTS` array on the Python side and template it into the shim at startup. Could read from the same `Agent._DECISION_EVENT_NAMES` so there's one source of truth. Out of scope for the port; flag for a future hardening pass.

### C. Strict-mode end-to-end test isn't explicit

The spec asked for a "strict-mode-still-works regression" running through a faux-pi session. The validation logic is exercised in `test_agent_class.py` (subclass with `_raise_on_unhandled_event = True`), but I didn't see a test that runs an end-to-end faux-pi session covering all 18 + 19 events under strict mode.

Probably not necessary — the dispatcher's strict-mode branch is straightforward and the existing strict-mode test for unknown events covers the logic. But if we want belt-and-suspenders, add one during port.

### D. `_handler_wants_context` heuristic

`agent_class.py:468-484` decides whether to pass `ctx` based on parameter introspection. Edge cases:

- `def decide_X(self, event, *args)` → ctx passed (because `*args` matches).
- `def decide_X(self, event, **kwargs)` → ctx NOT passed (kwargs alone doesn't trigger; positional count = 1).
- `def decide_X(self, *args)` (no explicit event param) → ctx passed.

For the canonical signatures (`self, event` or `self, event, ctx`), behavior is correct. For weird signatures, the user might be surprised. Not a real-world concern; flag for the docstring.

### E. `subscribe_client_events` still has the v7 thread-bounce

The double-bounce I flagged in `2026-05-17-v7-analysis.md` § Discussion C is still present (owner thread → loop thread → list.append). v8 didn't simplify it because it didn't need to. We can do this refactor during port if we want; it's purely internal.

### F. Wire frame field names diverged

My prompt sketched `{"type": "event", "event_name": "...", "event_data": {...}}` and similar for `notify_event`. v8 uses `{"type": "event", "event": "...", "data": {...}}` (see `test_channel_separation.py:32-41` for the literal wire shape). Functionally identical, but the spec used different names. Nothing to change; just noting that ChatGPT made a small naming choice not constrained by the prompt.

## Recommendation for the libharness port

**Adopt v8 with the mixin refinement, close the gap, split into three files.**

v8 is structurally complete and well-tested. The mixin refinement applied in-tree (`agent_class_mca.py`) is the better organization for the port baseline. The 38-declaration gap should be closed during the port. A 3-file split groups related material naturally.

### File layout for the port

```text
src/libharness/pi/
├── events.py          (public)   — AgentEvent, HookContext, UnhandledEventError
├── hook_surface.py    (public)   — AgentHookSurface mixin
└── agent_class.py     (public)   — Agent class
```

**`events.py`** (~80 lines):

- `AgentEvent` dataclass.
- `HookContext` dataclass.
- `UnhandledEventError`.

These are the public data types hook authors interact with. Small, stable, no upward dependencies.

**`hook_surface.py`** (~250 lines once the gap is closed):

- The four frozensets (`_EVENT_NAMES`, `_DECISION_EVENT_NAMES`, `_OBSERVABLE_EVENT_NAMES`, `_RPC_REQUEST_TYPES`).
- Config class attrs (`_raise_on_unhandled_event`, `_decision_timeout_ms`, `_decision_timeouts_ms`).
- Hook type aliases (`AsyncAgentHook`, `SyncAgentHook`, `AsyncDecisionHook`, `SyncDecisionHook`).
- **All 112 hook ClassVar declarations**, in the four-quadrant order with comment headers.
- All `_validate_*` classmethods (they only read class-level state from the mixin; they belong with the surface they validate).
- (New) consistency-check helper that verifies every event in `_EVENT_NAMES` has `on_X` + `async_on_X` declared, and every event in `_DECISION_EVENT_NAMES` has all four flavors declared. Runs on the base `Agent` class at import time; catches drift if the sets and the literal declarations ever diverge. ~15 lines.

Imports `AgentEvent` (for type aliases) and `HookContext` (for decision-hook signatures) from `events.py`.

**`agent_class.py`** (~150 lines):

- `Agent` class with: `__init_subclass__`, `__init__`, `start`, `close`, dispatchers (`_async_on_event`, `_async_on_bridge_event`, `_dispatch_notification_hook`, `_dispatch_decision_hook`), lifecycle helpers, manifest wiring (`_initial_open_gates_for_class`, `_decision_timeouts_for_manifest`).
- Module helpers `_call_decision_handler` and `_handler_wants_context`.

Imports `AgentHookSurface` from `hook_surface.py` and types from `events.py`.

The 3-file split prevents the circular-import problem (the mixin's ClassVar type annotations want to reference `AgentEvent`, but `AgentEvent` lives in a downward-dependency module). All imports flow one direction: `agent_class.py` → `hook_surface.py` → `events.py`.
