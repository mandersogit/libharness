## Headline addition: decision hooks for pi's in-process event surface

Right now `Agent` exposes notification hooks (`on_X` / `async_on_X`) for events pi forwards over RPC stdout. But pi also has a second event surface — events it dispatches in-process only to TS extensions registered via `pi.on(event, handler)` — that lets handlers return a result pi consumes (block a tool call, modify a provider request payload, veto a session switch, etc.). I want Python to participate in this surface.

The event-bridge proposal in pi's docs and the `extensions/types.ts` source enumerate these. Examples: `tool_call` returns `{block?, reason?}`; `session_before_switch` returns `{cancelled?}`; `before_provider_request` returns a modified payload; `context` returns filtered messages; `tool_result` returns content/details mutations. Full list lives at `links/pi/packages/coding-agent/src/extensions/types.ts` (or wherever your build of pi keeps it).

### Architecture: subscribe-to-all + always-notify + gated-decide

The TS shim subscribes to **every** decision-shaped event up front via `pi.on(event, handler)`. Each handler always sends an event to Python on every fire, but the *shape* of that bridge call depends on whether Python has opted in to make a decision:

- **Gate closed** (Python hasn't opted in for this event): the shim sends `notify_event` fire-and-forget — pi doesn't wait for a response. Shim returns `undefined` to pi (pi proceeds with its default behavior, same as if no extension were subscribed). Python still hears about the event; it just doesn't gate pi's loop.
- **Gate open** (Python opted in): the shim sends `event` synchronously and waits for the response. Python runs its decision hook, returns a result that the shim hands to pi. Pi waits the whole time.

One bridge call per fire either way. The user gets full visibility for logging/monitoring regardless of whether they're gating anything. Pi only blocks when explicitly asked to.

Why this shape:

- Pi's handler contract is `(event, ctx) => Promise<R | void> | R | void` — a void return is indistinguishable from no handler, so an always-subscribed `() => undefined` costs nothing on pi's side beyond an empty function call.
- The participation events (`tool_call`, `before_provider_request`, `context`, `session_before_*`, `user_bash`, `input`, etc.) are low-frequency (1–10 per turn). Always-notify cost is in the noise.
- The gate is a per-event flag in the shim. Open at extension load based on what the Python side declared. Immutable for the lifetime of the run (we're deferring runtime opt-in).

### Decision hook naming and surface

Symmetric with notification hooks:

- `decide_<event>` — sync method, dispatched via the existing hook executor.
- `async_decide_<event>` — async method, awaited on the runtime asyncio loop thread.

A subclass defines **at most one** per event (just like `on_X` / `async_on_X`). Both defined for the same event is a `__init_subclass__` `TypeError`. Symmetric error semantics with the notification side.

A subclass may **also** define `on_X` for the same event in addition to one of `decide_X` / `async_decide_X` — observation and decision aren't mutually exclusive. When both are present and the gate is open, **notification runs first, then decision** inside the same bridge call. Decision return goes to pi.

### Opt-in trigger: method existence

`__init_subclass__` introspects the subclass for any non-None `decide_*` / `async_decide_*` attribute. The corresponding event names are the initial open-gate set, passed to the shim via the manifest. No separate `_DECIDE_EVENTS` list — the methods *are* the declaration. Matches how notification hooks declare themselves.

### Result shape: raw dict

Each decision event has a different return shape in pi's TS code (`{block?, reason?}` for `tool_call`, `{cancelled?}` for `session_before_*`, etc.). The Python decision hook returns a raw dict matching the shape pi expects, or `None` (treat as "no opinion, pi uses default"). No TypedDicts or per-event dataclasses in this pass — matches the existing raw-dict choice for `AgentEvent` payloads.

**Document the return shapes.** Read pi's TS source (`extensions/types.ts` or wherever the `EventHandlers` interface and Result types live) and produce a table in `AGENT_HOOKS.md` (or a new `DECISION_HOOKS.md`) mapping each decision event to its expected return shape with concrete examples. Without this, users have to grep pi's source to know what `decide_tool_call` should return. Critical for usability.

### Cancellation

Same cooperative pattern as `ToolContext.cancelled`: when pi closes the bridge connection mid-decision (e.g., the agent loop gets aborted while Python is processing a decision), Python's hook should observe a cancellation flag and return promptly. Your call on the exact API shape — second positional arg `ctx: HookContext` on decision hooks, or a flag on `AgentEvent`, or something else. Match the tool-side pattern where reasonable.

Notification hooks don't need cancellation (fire-and-forget; nothing to cancel). Asymmetry is fine if it keeps each shape clean.

### Timeout: no default, opt-in mechanism

By default, the shim waits indefinitely for the Python decision response. "Fail closed" is the right default for permission gates and audit — a hung hook blocks pi visibly rather than silently letting unauthorized actions through.

Provide a configuration mechanism for subclass authors who want timeouts. Concrete shape your call — likely either a single class-level `_decision_timeout_ms: ClassVar[int | None] = None` or a per-event dict `_decision_timeouts: ClassVar[dict[str, int]] = {"tool_call": 5000}`. Either is fine; pick whichever fits the existing class-attribute patterns better. On timeout the shim returns `undefined` to pi (treat as no opt-in for this fire) and logs a warning.

### Channel separation

Decision events arrive at Python via the bridge channel (shim → Python), not via pi's RPC stdout stream. `PiRpcClient.on_event(handler)` subscribers do **not** see decision events. Only the Agent class's `on_X` / `decide_X` / `async_decide_X` hooks observe them. This is by design — the bridge is a distinct channel from RPC, and decision events are participatory by nature.

Add a regression test that pins this. Subscribe a `client.on_event(handler)` listener; trigger a decision event end-to-end; assert the lower-level listener does NOT see it.

### Bridge protocol additions

The bridge currently has request types `manifest` and `execute`. Add:

- `notify_event` (shim → Python, fire-and-forget): payload is the event name and event data. Python's bridge server dispatches to the relevant `on_X` / `async_on_X` notification hook. Shim does not wait for a response (or if it does for connection-close cleanliness, that wait is decoupled from pi's loop — pi already got `undefined` returned from the handler).
- `event` (shim → Python, sync round-trip): same payload shape. Python dispatches notification hook first (if defined) and then decision hook. Returns the decision result. Shim hands the result to pi.

Manifest response gets a new field: `initialOpenGates: ["tool_call", "session_before_switch", ...]` listing events to gate-open at extension load.

**Protocol version stays at `1`.** The bridge isn't versioned beyond the existing handshake constant, but no shipped binary or distribution exists yet, so a bump would be ceremony with no protective value. The shim regenerates from `shim.py` on every extension load — no drift possible at our scale. Keep `MANIFEST_PROTOCOL_VERSION = 1` (but please *name* the constant; the previous revision inlined the literal `1` in the manifest dict — promote to a named module-level constant in `tools.py` with a docstring about when to bump).

### Hook exception handling

Currently a sync hook that raises propagates through `loop.run_in_executor`'s future, out of `_async_on_event`, out of `_dispatch_event`, up into `_read_stdout_loop` — and kills the reader thread. That's a real footgun. Wrap each hook invocation (notification AND decision) with `try/except + log`. A raising hook should be logged with the event type and stack trace but should not kill the reader or hang the harness. Same posture for both flavors.

For decision hooks specifically: if the hook raises, the shim should see the bridge call fail and return `undefined` to pi (fail-open for this fire, same as a timeout). Pi proceeds with its default.

## Additions to the notification hook set

In addition to the existing 10 named hooks (`agent_start`, `agent_end`, `turn_start`, `turn_end`, `message_start`, `message_update`, `message_end`, `tool_execution_start`, `tool_execution_update`, `tool_execution_end`), pi emits 7 more event types over RPC stdout that should be named hooks:

- `queue_update` — steering/follow-up message queue state changes.
- `compaction_start` — context compaction begins.
- `compaction_end` — context compaction completes (with `reason`, `result`, `aborted`, `willRetry`, `errorMessage` per pi source).
- `session_info_changed` — session name/info changed.
- `thinking_level_changed` — reasoning level changed.
- `auto_retry_start` — pi automatically retries after a recoverable error (with `attempt`, `maxAttempts`, `delayMs`).
- `auto_retry_end` — retry succeeds or exhausts.

Add `async_on_<event>` / `on_<event>` for each (literal declarations, no metaclass codegen — same pattern as the existing 10).

Source: `links/pi/packages/coding-agent/src/core/agent-session.ts` declares these around lines 124–140; cite the exact lines in `AGENT_HOOKS.md`.
