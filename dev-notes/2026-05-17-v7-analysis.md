# v7-threaded-agent-hooks — analysis

Analysis of the v7 follow-on revision the agent produced in response to `dev-notes/2026-05-17-v7-request.md`. The package is vendored at `dev-notes/predecessors/v7-threaded-agent-hooks/`. This document compares it against the spec and surfaces what's worth porting forward, what's worth pushing back on, and what's outright wrong (spoiler: very little).

## TL;DR

**v7 hit the brief cleanly.** Both carry-forward fixes landed correctly (with a stronger test than I asked for). The new `Agent` class implements the parallel-two-method pattern with all the validation, dispatch, and lifecycle behavior specified. All six tests I asked for are present, plus a bonus integration-style test. mypy strict + pyright basic + ruff are clean; 18/18 tests pass (1 skipped on the real-pi gate). Architecture from the prior reshaping is intact — no structural drift.

The agent made defensible judgment calls on every open question. There are 3–4 small things worth discussing before we port v7 into `libharness.pi`, but they're refinements rather than blockers.

**Recommendation:** port v7 into `src/libharness/pi/` as the new base. Adopt-as-is for the Agent class; consider the small refinements in § Discussion items.

## Carry-forward fixes — both correct

### Fix 1 — `set_model` wire field

- Method signature: `set_model(provider, model_id)` (`rpc.py:318`).
- Wire frame: `{"type":"set_model","provider":...,"modelId":...}`. Matches pi-mono `rpc-types.ts:31`.
- Regression test (`tests/test_set_model.py` + `tests/fake_pi_rpc.py:61–79`): the fake-pi server *actively rejects* requests that contain `"model"` and require `"modelId"`. That's a stronger guarantee than I asked for and a nicer regression than just observing the on-wire shape.

### Fix 2 — manifest `protocolVersion` handshake

- `protocolVersion: 1` included in the manifest response payload (`tools.py:261-263`).
- TS shim hardcodes `1` and throws on mismatch immediately after the manifest call (`shim.py:55-58, 203-205`).
- No explicit test exercises the mismatch path — I said that was welcome but not required, so this is fine. Worth adding when we port to libharness.

**Minor note:** v7 inlined the constant `1` in the manifest dict rather than defining a named `MANIFEST_PROTOCOL_VERSION = 1` at module level the way I asked. Functionally equivalent, but the named constant is what we already had in current `libharness.pi/tools.py:26`. Cheap to restore when we port.

## Open question resolutions (agent's choices)

The agent picked decisively on every open question and justified each in `docs/IMPLEMENTATION_JOURNAL.md` § "Agent hook pass".

### 1. Event set — focused 10-event set, sourced from pi's `packages/agent/src/types.ts`

The exposed named hooks are:

| Event                   | When it fires (agent's words)                                |
| ----------------------- | ------------------------------------------------------------ |
| `agent_start`           | Agent begins a prompt or continue run                        |
| `agent_end`             | Final low-level agent-loop event for the run                 |
| `turn_start`            | New turn begins (one provider response + tool calls)         |
| `turn_end`              | Turn completes with assistant message + tool-result messages |
| `message_start`         | User, assistant, or tool-result message begins               |
| `message_update`        | Assistant message receives a streaming provider delta        |
| `message_end`           | Message completes                                            |
| `tool_execution_start`  | Tool call selected; execution starting                       |
| `tool_execution_update` | Tool emits partial/progress result                           |
| `tool_execution_end`    | Tool call finishes with final or error result                |

Session-level, extension UI, and RPC response events are intentionally left to the lower-level `client.on_event()` plumbing.

**Verdict:** sensible. The names match what pi actually emits at the agent-loop layer. The naming mismatch worth flagging: my prompt mentioned `tool_call`/`tool_result` as informal examples, and v7 chose the more accurate `tool_execution_start`/`tool_execution_update`/`tool_execution_end`. We should verify these names match the current pi-mono source before porting — see § Verification items.

### 2. `Agent` vs `PiAgentHarness` — inheritance

`class Agent(PiAgentHarness)`. One object; subclasser overrides hooks and calls `agent.start()` / `agent.prompt(...)`.

Rationale: simpler for v1; if multi-harness-per-agent ever becomes a real need, we can introduce a composition variant later without breaking the inheritance API.

**Verdict:** correct call. Matches what I leaned toward in the request.

### 3. Event payload — `AgentEvent` frozen wrapper over raw dict

```python
@dataclass(frozen=True, slots=True)
class AgentEvent(Mapping[str, Any]):
    payload: dict[str, Any]
    @property
    def type(self) -> str: ...
    def __getitem__/__iter__/__len__: ...  # Mapping protocol
```

User code can write `event.type`, `event["message"]`, `event.get("foo", default)`, or `event.payload` for the raw dict.

**Verdict:** good compromise. Avoids the "one dataclass per event" surface inflation while still giving `event.type` ergonomics and proper `Mapping` typing. The pi event taxonomy is fluid enough that this is the right level of abstraction for v1.

**Small caveat:** `AgentEvent` is frozen *at the dataclass level*, but `event.payload` is a mutable `dict`. A user could do `event.payload["foo"] = "bar"` without an error. Probably fine — nobody should be mutating event payloads — but worth a docstring warning. `from_mapping` does a defensive `dict(event)` copy on construction so the user can't accidentally share state with whatever produced the event upstream.

### 4. Lifecycle wiring

- `Agent.start()` calls `PiAgentHarness.start()` first, then installs the dispatcher via `self._call(lambda core: core.subscribe_client_events(self._async_on_event))`.
- `Agent.close()` uninstalls before closing the underlying harness.
- Two new owner-thread methods on `_PiAgentHarnessCore`: `subscribe_client_events` and `unsubscribe_client_events` (`agent.py:412-431`).

**Verdict:** correct. The dispatcher is additive on top of `PiRpcClient._event_handlers`, not a replacement. Per-event ordering is preserved by the async dispatcher's sequential `await`.

**Mild critique:** `subscribe_client_events` bounces through the owner thread to then schedule a coroutine on the loop thread, which calls `self.pi.on_event(handler)` (a synchronous `list.append`). That's a lot of thread hops for what's effectively a synchronized list append. The owner-thread discipline is the right pattern in principle, but the unsubscribe path is even worse — it bounces through the owner thread, schedules an async coroutine on the loop thread, which then calls `unsubscribe()` (also a synchronous list operation). Could be simplified to "submit the append/remove to the loop thread directly." Not a correctness issue; just churn.

## Discussion items

Small things worth thinking through before we port v7 into `libharness.pi`.

### A. Event-name verification against current pi-mono

v7's `_EVENT_NAMES` is sourced from pi's `packages/agent/src/types.ts`. We should grep current pi-mono (`links/pi/packages/agent/src/types.ts` or wherever the event union lives now) to confirm the 10 names match what pi *currently* emits. If pi has renamed any event since the agent generated v7, our `_EVENT_NAMES` is stale on day one.

### B. Named constant for `MANIFEST_PROTOCOL_VERSION`

v7 inlines `1` in the manifest dict (`tools.py:262`) instead of declaring `MANIFEST_PROTOCOL_VERSION = 1` at module level. Current libharness has the named constant with a comment about when to bump it. Worth restoring the named-constant pattern when we port.

### C. `subscribe_client_events` could be simpler

The owner-thread + loop-thread double-bounce for installing/removing a simple list subscription is over-engineered. A direct `self.runtime.run_async(self._add_subscriber(handler))` from `Agent.start()` would skip one hop. Not urgent; the owner-thread discipline is defensible. Worth considering during port.

### D. `AgentEvent.payload` mutability

The wrapper is `frozen=True, slots=True` but `payload: dict[str, Any]` is internally mutable. A user can mutate via `event.payload["foo"] = "bar"`. The defensive `dict(event)` copy in `from_mapping` prevents shared state with the producer, but doesn't prevent the user shooting their own foot. Options: switch to `MappingProxyType`, or add a docstring note. Lean toward docstring + don't-do-that — `MappingProxyType` is awkward at the typed-dataclass layer.

### E. No protocolVersion-mismatch test

The TS shim asserts and throws on mismatch, but no test exercises this path. Cheap to add (build a Python server that returns `protocolVersion: 99`, launch a real pi against it, assert pi reports the shim load failure). Add when porting.

### F. Sync hook exception handling

A sync hook that raises propagates through `loop.run_in_executor(...)`'s future. `await fut` re-raises in `_async_on_event`. That bubbles up to whoever invoked `_async_on_event` — which is the `client.on_event` callback chain. Currently, the existing v5/v6 dispatch path doesn't catch exceptions from event handlers; a raising hook *will* kill the reader loop. This is the same behavior as raising in a `client.on_event(handler)` subscriber today, so v7 didn't introduce the issue — but the `Agent` API makes it easier to accidentally trip. Worth a note in `AGENT_HOOKS.md` and maybe a `try/except + log` around the hook invocation. Not a blocker.
